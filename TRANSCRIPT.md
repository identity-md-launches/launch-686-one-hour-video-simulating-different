# IMD Swarm Field Guide

Educational simulation. No live jobs, signatures, addresses or payments.


## 00:00 — Start here

### 00:00 — Welcome to the swarm

A one-hour guided simulation of requests and outcomes. Every job, quote, address and result shown here is illustrative. We do not connect a wallet or submit paid requests. The aim is to help you choose a tile, write a useful brief, follow progress and evaluate the delivered work.

### 00:30 — The current menu

Launch a company combines contracts, token and site. Ask the oracle requests a signed answer. The one-part tiles are Token, Contracts, v4 hook, Audit, Report, Website, Image, Audio and Video. Heartbeat is visibly marked Soon. We will cover all of them, including a clearly labeled scheduling preview.

### 01:00 — A shared workflow

The page organizes requests into Choose, Describe, Check and Pay. Choose the smallest option that fits your goal. Describe observable behavior. Check the request before payment. Read the resulting quote before authorizing it. A successful check means the brief can proceed; it does not mean the work has already been delivered.

### 01:30 — Simulation: choose a route

A neighborhood repair club needs memberships, a token and a public dashboard. This is our fictional company, Repair Club. Choose Launch a company for the integrated package. If the club only needs a poster, choose Image. If it only needs a sourced explanation, choose Report. Avoid buying an entire package for a single artifact.

### 02:00 — Write a checkable brief

Say who the user is, what they can do, what inputs the work needs and what successful delivery looks like. For our club: a member can view dues and membership status; an administrator can update a fee; the site shows the configured contract addresses. These requirements are more useful than simply asking for an amazing company.

### 02:30 — Check before paying

The live page says: The check reads the request the way the quote will: what the swarm will do, what the builders know, and anything that would stop it. Nothing is paid. In this simulation, a check catches a missing owner address. We revise the brief before opening the payment step.

### 03:00 — Quote review

Treat the quote shown by the live application as the authority for price, asset, network, scope and expiry. This lesson invents no fixed fee. Compare the quoted work with your brief. If you revise the scope, inspect the new check and quote. An accepted payment opens work; it is not evidence of final delivery.

### 03:30 — Follow the work

Use Explorer jobs to follow the accepted request and its available records. Use Published to look for released artifacts, Oracle for answer records and Heartbeats for scheduled runs where available. This film compresses those stages into teaching cards. It does not claim that every real request finishes in the time shown on screen.

### 04:00 — Inspect the outcome

Download or open the delivered artifact and compare it with your acceptance criteria. A website should load; a report should support its claims; a video should have the requested duration and codecs. A status label alone cannot establish usefulness. Record what passed, what failed and the exact revision you need.

### 04:30 — Pause and choose

Practice: you need an answer to a yes-or-no question, an illustration and a deployed contract. Which routes would you choose? Use Oracle for the answer, Image for the illustration and Contracts for the contract project or launch path. Keep three deliverables distinct unless a company package truly matches the integrated goal.

## 10:00 — Ask the oracle

### 10:00 — Choose the answer route

Ask the oracle is labeled A signed answer. Use it for a specific question with a defined answer type. Choose Report when you need a longer explanation with sources. A signed answer can be used by a system that understands its format; the signature alone does not prove that an ambiguous question has one objective interpretation.

### 10:30 — Define the question

Our fictional example asks: in the supplied Repair Club event record for period A, did at least twelve distinct members attend? We define period A, the record and how repeat visits are counted. This is an invented dataset rather than a historical fact claim. A question without the period or counting rule could produce incompatible answers.

### 11:00 — Choose an answer type

The loaded launch client lists yes or no, a number, text, a list of text, an address and a list of addresses. These correspond to bool, uint256, bytes32, bytes32 array, address and address array. Choose the type your consumer expects. A Boolean question should not require a paragraph where the caller expects true or false.

### 11:30 — Simulation: Boolean answer

The fictional record contains fourteen distinct members. Under our stated threshold of twelve, the illustrative Boolean outcome is true. This answer is not submitted to the live Oracle and has no real signature. In a real request, inspect the returned answer record and the verification information available for it before connecting it to another system.

### 12:00 — Simulation: numeric answer

Change the question to: how many distinct members attended in period A? The intended numeric answer in the same fictional record is fourteen. Define the unit as distinct members, not visits. Specify treatment of duplicate identifiers. A numeric answer becomes easier to check when the question states exactly what should be counted and what source should be read.

### 12:30 — Simulation: text answer

For text, ask for a short identifier rather than a full essay. Example: return the winning workshop code from the supplied scoring table. The fictional outcome is WREN. A bytes32 field has a bounded byte length, so long natural-language responses belong in a report. Here we display human-readable text without fabricating an encoded signed response.

### 13:00 — Simulation: address answer

For an address, identify the chain, registry and exact lookup rule. Example: which owner address is recorded for the supplied demo contract at the specified snapshot? This film intentionally shows no invented address masquerading as a real lookup. The useful outcome would be a verified address value associated with that precise source and snapshot.

### 13:30 — Panel and scope

The client includes a panel-size setting. Use the limits and default visible in the current form rather than assuming unlimited reviewers. A larger panel does not repair a missing definition, missing source or wrong answer type. First make the question reproducible, then inspect the form settings and resulting quote for the request you actually intend.

### 14:00 — Ambiguity and retry

Bad question: is Repair Club doing well? Revised question: does the supplied period A record show at least twelve distinct members under the stated deduplication rule? Our illustrative first attempt needs clarification. The revised attempt yields the fictional true outcome. A precise question makes disagreement easier to investigate and the answer easier to consume.

### 14:30 — Oracle checkpoint

Practice choosing types: a threshold uses Boolean, a count uses number, a short label uses text and an owner lookup uses address. Ask whether you need a signed value or a researched document. Keep the source, time window, unit and fallback for unavailable evidence explicit. Our simulated values are examples, not live Oracle results.


## 15:00 — Heartbeat preview

### 15:00 — Availability comes first

Heartbeat is marked Soon and disabled on the launch page captured for this lesson. The page also links to existing Heartbeats and their runs. Viewing a history does not mean the new-request tile is enabled. This chapter is a planning simulation for recurring work, not a claim that you can start it from this screen today.

### 15:30 — Pick a repeatable goal

A scheduled request should have a stable rule that still makes sense at each run. Example: summarize new club proposals since the previous successful report. The time window advances, but the output template stays the same. A vague instruction such as keep an eye on everything leaves the recurring job with no measurable completion condition.

### 16:00 — Simulated schedule brief

Preview brief: every day at a stated UTC time, produce a sourced proposal digest containing title, author, status and changes since the previous run. Use a configured proposal source. Mark unavailable sources explicitly. This is a design exercise. Confirm the actual schedule controls and supported request kinds when Heartbeat creation becomes available to you.

### 16:30 — Define windows

For a daily digest, define the start and end of each interval and how boundary events are counted. A half-open interval avoids counting one event twice. If a run fails, state whether the next run should catch up from the last successful window. Without that rule, recurring output can silently omit or duplicate information.

### 17:00 — Simulated first run

Run one covers the fictional first period and produces a digest of three proposals. Each entry links to its source and records the cutoff. This demonstrates the kind of artifact you would inspect. No live schedule, job, charge or proposal lookup happens here. A real run must be judged against the source records for its own window.

### 17:30 — Simulated second run

Run two contains one changed proposal and one new proposal. The desired digest marks the change rather than copying the previous report. Compare timestamps and identifiers to catch duplicates. Recurring work is useful when it reduces manual repetition while keeping its evidence visible. It is less useful when it simply repeats stale output on a timer.

### 18:00 — Simulated failed run

Run three cannot reach its source. The desired outcome records source unavailable and the affected window; it does not invent updates. Our preview then plans a retry or catch-up report. The live product may expose different failure and retry controls. Learn those controls before depending on a recurring request for a consequential workflow.

### 18:30 — Runs and funding

The loaded client includes schedule creation and top-up concepts, but the visible Heartbeat tile is Soon. Plan a finite run budget and a way to observe remaining runs when the feature is available. Do not assume perpetual execution or a fixed price. Read the actual quote and schedule summary rather than relying on this preview.

### 19:00 — Stop and revise

A repeating task should have a clear owner and a review point. If the source changes or the digest is no longer useful, revise or stop it using the controls actually available. This preview does not promise a particular cancellation or refund mechanism. Check how the live feature handles unfinished runs before committing a recurring budget.

### 19:30 — Heartbeat checkpoint

Write a recurring brief with a cadence, timezone, source, interval rule, output template, run budget and unavailable-source behavior. Then distinguish the planned outcome from current availability. The launch page currently says Soon. Until the creation route is enabled, use this plan as a draft and inspect existing histories to understand what a run record looks like.

## 35:00 — Audit

### 35:00 — Choose Audit

The loaded client says: Your contracts, audited as they are. Nothing is changed or deployed. This makes Audit a review route. Use it to assess a specific existing codebase. Do not expect the audit itself to repair findings or launch a new contract. Separate the requested assessment from any later implementation work.

### 35:30 — Pin the target

Provide a repository and exact revision, files in scope and the relevant deployment context. Our fictional target is Repair Club revision A. If the code changes while the audit is running, the report may no longer describe the latest version. A pinned target lets a reviewer and reader refer to the same implementation.

### 36:00 — Describe the intended behavior

Give the auditor the permission model and invariants. Example: only the owner updates membership and revocation must remove active access. A reviewer needs to know what the code is supposed to enforce. Otherwise, a deliberate product choice and an accidental vulnerability can look similar. Include known assumptions rather than hiding them inside vague product language.

### 36:30 — Simulation: scope check

The initial request links an entire monorepo without naming contracts. Our mock check asks for the relevant directory and revision. We narrow scope to MembershipRegistry and its tests. This does not prove other files are safe; it makes the review boundary explicit. The quote should match that boundary before payment.

### 37:00 — Simulation: findings

Our fictional audit finds missing owner authorization in revokeMember. The illustrated finding includes affected function, impact, reproducible condition and recommended remediation. This is invented teaching material, not a claim about an actual Repair Club repository. A useful audit outcome connects each finding to evidence so the implementer can reproduce it.

### 37:30 — Severity and evidence

Read severity alongside impact and preconditions. A scary title without an attack path is insufficient. A low-severity label can still matter for your use case. Ask whether the report distinguishes confirmed findings, design questions and unsupported assumptions. Good evidence helps you decide which changes to prioritize without relying on the label alone.

### 38:00 — Illustrative report outcome

Inspect its check and quote rather than assuming that the original Audit payment automatically includes remediation.

### 39:00 — Review the revised version

After a fix, compare the revised source with the audited revision and rerun the relevant checks. A finding resolved in one function does not mean unrelated changes have been reviewed. Ask for a targeted reassessment if needed. Keep the report, fix reference and evidence together so readers can see which version each statement describes.

### 39:30 — Audit checkpoint

Before ordering Audit, identify the code revision, files, intended behavior and exclusions. After delivery, inspect reproducible evidence and target version. Remember the explicit route boundary: nothing is changed or deployed. The useful outcome is a review artifact that informs a subsequent decision, not an automatic upgrade to your contracts.
